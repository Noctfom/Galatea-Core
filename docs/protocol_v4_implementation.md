# Galatea V4 协议实施规格

> 状态：实施中。本文件是 V4 实现分支的可执行规格；已发布的 V3 行为仍以现有架构文档为准。

## 1. 版本边界

| 项目 | 当前稳定值 | V4 目标值 | 切换时机 |
| --- | ---: | ---: | --- |
| 框架版本 | 3.9.1（阶段 3 批次 2 已完成） | 3.9.x；接入组卡/BO3 上层后 4.0.0 | 按发布阶段更新 |
| Model Protocol | 4 | 4 | 已在精确卡片身份合入时切换 |
| Checkpoint Format | 3 | 3 | V4 必需元数据已落地 |
| Trajectory Schema | 尚未独立维护 | 1 | 规范轨迹记录器落地时 |

模型协议、检查点容器、轨迹格式和框架版本彼此独立。开发期间一旦启用 Model Protocol 4，不再递增该协议号；所有后续 V4 修补通过字段清单、形状和 `protocol_schema_hash` 防止开发中间产物混用。

V4 从头训练，不迁移 V3 权重、优化器、混合精度状态或历史模型池。V3 模型及其 Link 接口继续由旧版运行包维护。

## 2. 不可破坏约束

- 不向模型泄漏对手手牌、卡组顺序或其他非公开信息。
- 任意模型动作必须能够确定性地还原成当前 Core 提示的合法响应。
- 训练、竞技场、ONNX 和 Link 必须使用同一套观测及动作构造器。
- 相同公开状态在玩家视角互换后必须保持字段语义对称。
- 静态 Lua 语义以卡片代码和效果槽为索引，不把卡面描述序号当作 Lua Effect 序号。
- 初始 V4 网络基线保持 `512 / 8 heads / 6 layers`，先验证协议收益，再扩大网络。
- 首轮 V4 不引入 MCTS、不引入无法可靠清理的持续效果追踪器，也不添加主观的攻击、召唤或盖放奖励。
- 数学等价的内存、传输和批处理优化可以进入 V4，但必须有数值对照测试。

## 3. 目标数据协议

### 3.1 精确卡片身份

- 使用只追加、不重排的 `card_vocab.json` 映射真实卡片代码，移除取模哈希碰撞。
- `0` 保留为填充，`1` 保留为未知卡，`2/3` 保留为对手隐藏手牌/魔陷占位；真实卡片从 `10` 开始，新增卡只能追加到词表尾部。
- `protocol_schema_hash` 只描述固定容量、保留编号和输入结构，不因合法尾部追加而变化。
- 检查点、ONNX、制品清单和部署包记录训练时的词表哈希与卡数；加载时要求该映射是当前权威词表的精确前缀。
- 一个模型谱系必须使用跨机器唯一的只追加编号权威。默认同步仓库文件；自制卡用户可改用自建词表源或从本地 CDB 追加，但必须向该谱系所有机器分发同一文件。CDB 暂时领先时只隔离受影响卡组，不阻断其余环境。

### 3.2 全局与玩家状态

显式区分 `decision_player`、`turn_player`、`starting_player`、相对视角的 `went_first` 与 `is_my_turn`、绝对/自身/对手回合计数，以及阶段、区域和表示形式的离散类别。阶段、区域和表示形式不得继续用任意数值除法伪装成连续量。

### 3.3 动作语义

每个候选至少包含提示类型、操作族、来源角色、目标角色、精确卡片身份、效果槽、召唤方式、目标阶段、响应语义、选择上下限、完成/取消条件和 Core 回包数据。

操作族需明确覆盖通常/上级/特殊召唤、改变表示、怪兽盖放、魔陷盖放、发动、连锁、攻击/直接攻击、阶段切换、选择/取消选择、完成、取消、区域、指示物、排序、宣言及 Yes/No。融合、仪式、同调、超量、连接和灵摆不得合并为无标签的“特殊召唤”。

Type 26 保持 Core 原生逐次 Select/Unselect；静态组合消息保持一次返回完整合法组合。两类消息不得共享状态机。

阶段 2 批次 1 已落地以下字段契约：

| 字段 | 公开性与来源 | 生命周期/缺省 | dtype / 形状 | 消费者 |
| --- | --- | --- | --- | --- |
| `act_operation` | 当前公开提示；`MSG_SELECT_IDLECMD` 固定列表序号等 Core 候选族 | 当前合法动作快照；`DEFAULT=0` | `uint8 [120]` | 动作签名、策略网络、ONNX、回放 |
| `act_summon_method` | 当前公开提示；Core 消息或经验证运行上下文的直接证据 | 当前合法动作快照；非召唤为 `NONE=0`，泛特殊召唤为 `SPECIAL_UNKNOWN=3` | `uint8 [120]` | 动作签名、策略网络、ONNX、回放 |

标准 Core 的 `MSG_SELECT_IDLECMD` 六个列表依次证明通常召唤、特殊召唤、改变表示、盖放怪兽、盖放魔陷和发动。它不携带精确的特殊召唤方式，也不证明通常召唤是否需要解放。融合、仪式、同调、超量、灵摆、连接、上级召唤等枚举只为未来直接证据预留；来源区域与怪兽卡片类别不得充当召唤方式。原始 `(候选序号 << 16) | 列表类型` 仍由动作确定性还原，策略字段不改变 Core 响应。

阶段 2 批次 2 固定以下选择边界：Type 26 是唯一在本批次逐项 Select/Unselect 的协议；Type 15、20、23 必须一次返回完整组合。Type 20 的 `min` 是解放值下限而非卡片张数，Type 23 没有取消响应。Type 20/23 先提供单素材 Pass1 候选，再由同一合法性生成器构造组合；每个响应在入池和发包前按 Core 等价规则校验。`set_responseb` 使用完整 512 字节保活区，不再截断到 64 字节。

### 3.4 公开关系

公开观测至少表示装备目标、叠放关系、目标关系、素材关系、控制权、禁用区域和带类型的指示物。只记录 Core 能确定的当前公开事实，不猜测已经离场且无法判定失效时点的持续效果。

3.8.2 已通过当前随包 Core 的公开旧式 `query_card/query_field_count` 消费动态卡名、等级/阶级、攻防与基础攻防、原因/原因卡、装备目标、取对象关系、完整叠放素材、带类型指示物、原持有者、动态刻度/连接值，以及 `STATUS_DISABLED | STATUS_FORBIDDEN | STATUS_PROC_COMPLETE`。墓地和除外区也在决策快照前查询校准；对手隐藏卡的 Core 动态状态和关系在编码前统一遮罩。简易记牌器可以保留已经公开过的卡片身份及其静态 CDB/语义资料，但不会借此读取隐藏后的动态攻防、类型、指示物、素材或状态。原因、指示物类型与禁用区域按字节无损存入轨迹，网络前向时才展开，避免 PPO 轨迹池保存冗余 bit 矩阵。

等级、阶级与连接值虽然在 CDB 的 `level` 整数中复用存储位，但 Core 运行时查询是三个独立字段。普通/融合/仪式/同调怪兽通常只有 `level`，超量怪兽通常为 `level=0, rank>0`，连接怪兽通常为 `level=0, link_rating>0`；0 表示该概念不适用，不是缺失值。动态效果造成的例外完全服从 Core 查询，不由框架按卡类回填。

`STATUS_PROC_COMPLETE` 是 Core 用于苏生限制的“正规手续完成”权威位：正规出场成功时置位，进入墓地或除外仍保留，回到手牌/主卡组/额外卡组或召唤被无效时由 Core 清除。它应作为所有当前可见怪兽卡个体的持续字段，而不是根据移动消息推断。

Core 还在卡片对象上维护精确召唤类型、来源与玩家，公开 Lua API 也能供规则脚本读取；但截至上游 v11.0，标准查询字段仍未向客户端导出这些值。Galatea 不修改本地 Core、不维护私有二进制，也不根据卡类、来源区域或消息顺序猜测。当前模型只接收公开 `STATUS_PROC_COMPLETE`；精确召唤来源列为上游 API 待办，可向公开仓库提交 PR，待正式接口发布后再整体适配。最新上游已使用结构化 `OCG_DuelQuery`，未来迁移必须同时适配其公开 ABI 与 TLV 查询格式，而不是只替换一个字段解析器。

宏选择器现在对场上、墓地和除外区的卡片始终保留物理个体；隐藏/重置区只有在卡密、提示参数和已知公开状态完全一致时才折叠副本。组合仍受 5,000 项上限和既有加权缩减控制，不改变合法回包。

### 3.5 静态语义

Lua 静态语义移至模型侧查表，以精确卡片身份和效果槽索引。逐步轨迹只传身份、槽位和必要的动态覆盖信息，避免每个样本重复携带同一大块语义向量。

3.9.0 建立统一静态语义编译器、逻辑前缀身份及制品校验。3.9.1 将静态表注册到模型侧：Encoder、共享内存和 PPO 轨迹只传已有卡片 token，以及连锁/历史所需的紧凑效果槽 ID；模型在设备侧还原与旧展开输入逐元素一致的语义。未知槽位仍回退整卡，不改变可见信息与动作逻辑。

### 3.6 卡组协议

- 初始主卡组、额外卡组和 Side Deck 使用独立分区与数量标签。
- 单局策略只接收自己可知的卡组资料；不泄漏对手完整构筑。
- 初始卡组画像在一局内稳定，当前剩余卡组另用数量/掩码表示。
- Worker 每局只登记一次卡组画像，逐步数据引用 `deck_profile_index`。
- Side Deck 在 BO1 决斗策略中保留接口但不参与当前动作决策。

## 4. 目标网络结构

### 4.1 可复用 Deck Encoder

Deck Encoder 读取带主卡组/额外卡组/Side Deck、数量及角色标签的无序卡片集合，默认使用 8 个可学习 latent query，输出 `deck_style`、`deck_latents` 和 `per_card_features`。编码器必须通过卡片顺序置换不变性测试，并提供独立调用接口。

### 4.2 分层 FiLM

全局时局信息和稳定卡组风格使用不同分支，并在每个 Transformer 层、注意力子层和 FFN 子层分别产生调制参数：

`global_film + deck_gate * deck_film`

`deck_gate` 零初始化，调制幅度受限，并保留少量 deck-condition dropout，避免训练初期卡组分支覆盖基础状态判断。卡组摘要仍直接进入策略头和价值头，FiLM 不是唯一信息通道。

### 4.3 紧凑事件历史

保存最近 16 个“模型决策之间的状态转移事件”，而非简单保存最近 Core 消息。事件包含执行者、回合/阶段、提示/操作、来源/目标/效果槽/召唤方式/连锁、LP 与区域变化，以及取消、重试、无效、结算等结果。历史使用独立轻量编码器，不占用主棋盘 token 配额。

### 4.4 结构化辅助头

辅助输出分为状态级（纯胜率、终局原因、剩余长度、下一阶段、回合末资源变化）、动作级（取消/重试风险、短期状态与 LP 变化、下一事件、连锁或召唤结果）和卡组级（主卡/额外兼容、先后手表现、召唤与终端画像、遮盖卡恢复）。

每个头必须有可验证标签和缺失标签掩码。辅助梯度总量以主任务梯度的约 10%～20% 为初始范围；标签可靠性不足的头只作探针或停止向主干反传。

### 4.5 目标与过程表示

训练数据从下一决策、连锁结束、回合结束和终局四个尺度生成未来摘要。Goal Planner 根据当前状态、卡组表示和全局信息产生 `plan_latent`，策略条件变为：

`policy(action | state, deck_style, plan_latent)`

首版 `plan_latent` 每个决策点重新计算，并通过同回合/同阶段一致性约束减少无意义抖动；只有在该方案被验证后，才考虑持久 Option 或树搜索。

## 5. 训练与数据

- 初始奖励保持现有胜负主奖励及已确认的极端死锁约束，不新增行为偏好塑形。
- `gamma` 维持 `0.998`；优先验证 GAE `lambda=0.98`，并与 `0.95`、`0.99` 做受控对照。
- PPO 每批最多 4 个 epoch，并以目标 KL 提前停止；记录实际 epoch、KL、clip fraction 分位数和模块梯度。
- Core 维护唯一规范轨迹解释器；在线 Link 和 YRP 回放都只向该解释器提供原始消息、响应及来源元数据。
- YRP 只有在能够完整确定性回放、且每个响应唯一映射到合法候选时才进入行为克隆数据。
- 训练/验证数据按整局、卡组和玩家切分，禁止把同一局的相邻状态拆到不同集合。

规范轨迹至少记录卡组/Side Deck、随机种子、原始消息与响应、玩家角色、结果、Core/脚本/CDB/语义/词表哈希、数据来源和质量标记。

## 6. 上层组卡与 BO3 预留接口

V4 Core 提供独立的 `DeckSpec`、`MatchContext`、`DuelSummary`、Deck Encoder 和快速评估接口。未来上层模块负责合法构筑编辑、BO3 局间先后手与换备、对手构筑后验、模拟/反事实胜率评估，以及结合自己卡组、对手公开卡和比赛上下文动态生成 Type 142 宣言池。

Match Controller 位于单局 `DuelState` 外部；完整 BO3 回报不直接穿过全部底层决策反向传播。

## 8. 验收门槛

### 每次不兼容协议修改

- 输入字段、dtype、形状、掩码、枚举和值域均有测试。
- Core 响应往返测试证明选择结果保持合法。
- 隐藏信息测试证明没有新增泄漏。
- 玩家换位、卡组置换和确定性回放测试通过。
- PyTorch 与 ONNX 输出在定义的容差内一致。
- 旧协议检查点在分配完整网络前被明确拒绝。

### V4 短训前

- RuleBot 自检 1,000 局无解析崩溃、死锁和非法响应。
- V4 自博弈、V4 对 RuleBot、固定 V3 外部基准均可完成。
